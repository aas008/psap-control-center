# CSV → OpenSearch local prototype

This is the reproducible local prototype for the 2026-11-04 decision to test an
OpenSearch-backed store with a CSV-compatible read path. It uses the current
staging S3 object, not the older local snapshot.

## What it proves

- OpenSearch 3.9.0 can ingest the full RHAIIS CSV (35,998 rows × 56 columns).
- The index can be exported back to a byte-faithful CSV with 0 cell mismatches.
- The existing Streamlit dashboard renders the exported CSV identically to the
  original (same body text hash, same KPI values).
- The agent's `load_rhaiis_data()` reads the exported CSV unchanged (35,998 × 57,
  adding its derived `efficiency_ratio`).
- Exact filters, case-insensitive substring, top-N, version aggregation, version
  rename, idempotent upsert, add-field, and type-change behavior were measured.
- A per-run `dashboard.csv` can be bulk-indexed into the existing index with
  stable document IDs; redelivering it does not duplicate rows, and the
  consolidated CSV regenerated from the index matches the original.
- A second index for llm-d plus a read alias across both works for cross-project
  queries while keeping each project's own mapping.

## Setup

```bash
docker run -d --name psap-opensearch \
  -p 9200:9200 -p 9600:9600 \
  -e "discovery.type=single-node" \
  -e "DISABLE_SECURITY_PLUGIN=true" \
  -e "DISABLE_INSTALL_DEMO_CONFIG=true" \
  -e "OPENSEARCH_JAVA_OPTS=-Xms1g -Xmx1g" \
  opensearchproject/opensearch:3.9.0

mkdir -p data out
aws s3 cp s3://psap-dashboard-data/staging/rhaiis-dashboard/consolidated_dashboard.csv \
  data/consolidated_dashboard_s3.csv
aws s3 cp s3://psap-dashboard-data/staging/llmd-dashboard/llmd-dashboard.csv \
  data/llmd-dashboard_s3.csv

python3 -m venv venv
./venv/bin/pip install opensearch-py pandas python-dotenv pydantic-settings structlog
```

## Run

```bash
./venv/bin/python 01_create_index_and_ingest.py
./venv/bin/python 02_roundtrip_csv.py
./venv/bin/python 03_query_battery.py
./venv/bin/python 04_incremental_ingest.py

```

## Results

- 35,998 documents indexed in ~5 s.
- CSV round-trip: exact (0 cell mismatches), same 56 columns and row order.
- Exact version count: 1,829/1,829.
- Case-insensitive model substring: 3,797/3,797.
- Top-10 throughput: exact.
- Top-10 average throughput by version: exact **after**
  `shard_size: 1000`; the default `shard_size` returned a partial bucket
  (`vLLM-0.22.0` 5 rows instead of 62).
- Rename version by UUID: 5 rows updated, 5 verified.
- Re-index same `_id` twice: count stays 35,998.
- Add field: works. Change `version` keyword → text: rejected; reindex needed.
- `from: 10000` pagination: rejected by `index.max_result_window`.
- Incremental onboarding of a real 4-row per-run CSV: rows removed first to
  simulate a new run, then bulk-indexed in ~30 ms. Total returned to 35,998.
  Redelivering the same file twice kept the count at 35,998. Regenerating the
  consolidated CSV took ~1.1 s and matched the original row-for-row (ignoring
  order).
- llm-d index: 454 documents × 53 columns; 47 columns shared with RHAIIS;
  round-trip exact.
- Read alias `psap-all-benchmarks`: 36,452 documents (35,998 + 454). Top-5
  models by document count through the alias matched the pandas baseline
  exactly. `exists: EP` returned 454 documents (llm-d only). A write through
  the alias was rejected because no index is marked `is_write_index`.

## Incremental onboarding

Forge currently appends a run by downloading the full consolidated CSV,
concatenating the per-run `dashboard.csv`, and re-uploading it
(`projects/rhaiis/postprocess/s3_dashboard.py`). With OpenSearch the same
per-run file is a `_bulk` of its rows:

- each row becomes one document with an `_id` derived from its content (plus an
  occurrence suffix for exact duplicates), so redelivery is idempotent;
- two jobs finishing at once cannot overwrite each other, because they write
  different documents instead of the same S3 object;
- the consolidated CSV becomes a projection regenerated by
  `02_roundtrip_csv.py`, not the system of record.

A per-run batch is not atomic: a failed bulk can leave some rows indexed.
Retrying is safe because IDs are stable; "replace run" should `delete_by_query`
on `uuid` (optionally plus profile) before the bulk.

## Multiple projects: one cluster, many indices

| Name | Kind | Contents |
|---|---|---|
| `psap-rhaiis-benchmark-v1` | index | 35,998 docs, 56 columns |
| `psap-llmd-benchmark-v1` | index | 454 docs, 53 columns (47 shared) |
| `psap-all-benchmarks` | alias | read view over both |

Shared fields have the same mapping type in both indices, so aggregations work
across the alias. Fields that exist in only one index (for example `EP`) remain
queryable, but return only that project's documents. Writes through the alias
are rejected unless one index is marked `is_write_index`; write to the concrete
index instead.

## Persistence

The local OpenSearch container now uses a named volume:

```bash
docker volume create psap-opensearch-data
# mount it at /usr/share/opensearch/data
```

Saved objects (the `psap-rhaiis-benchmark-v1` index pattern and the **RHAIIS
table** saved search) live in OpenSearch’s `.kibana_1` index, so they survive a
container restart with the volume. Verified after `docker restart
psap-opensearch`: 35,998 documents and the saved search remained.

In the lab, persistence depends on the OpenSearch cluster’s PVCs, not the
Dashboards container. Save shared searches in the **Global** tenant (or a shared
tenant), not a private tenant, so other users can see them. A volume is not a
backup: use snapshots or saved-object export for that.

## Caveats

- The local container uses the `psap-opensearch-data` volume (see Persistence);
  deleting the volume still deletes the data.
- `terms` aggregations ordered by a sub-metric are approximate with the default
  `shard_size`; set it to at least the number of distinct terms.
- Full exports need `search_after`/PIT because of the 10,000-document window.
- The dashboard takes several seconds to load a 30 MB CSV and is blank until then.
- `_row_index` preserves the consolidated CSV's row order for the round-trip
  check. Production ordering should use a real sort key instead.
- Cross-index aggregations need the shared fields to have the same mapping type
  in every index; verify this before adding a project.
- The script simulates onboarding by deleting rows from the already-ingested
  index. Forge itself does not call OpenSearch yet; that integration is the
  next step.
